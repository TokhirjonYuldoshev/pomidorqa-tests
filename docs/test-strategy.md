# Стратегия тестирования на основе рисков

Цель проекта — давать понятный и воспроизводимый сигнал о качестве, а не просто увеличивать число автотестов.

PomidorQA — внешний учебный сервис. Поэтому отдельно рассматриваются три источника проблем: поведение продукта, состояние внешнего стенда и состояние тестовой инфраструктуры.

## Основные риски

| Область | Что может пойти не так | Основное покрытие |
| --- | --- | --- |
| Авторизация | неверный вход, потеря/утечка сессии, доступ анонимного пользователя к защищённым страницам | E2E авторизации и изоляции `BrowserContext` |
| Профиль | потеря данных, перезапись соседних полей, смешение аккаунтов | E2E сохранения, удаления и изоляции состояния |
| Свободные слоты | потеря слота, смешение слотов пользователей, неверная доступность | E2E управления слотами |
| Каталог | неверная фильтрация, дубли, неправильная видимость, устаревшее состояние | E2E поиска, граничных данных и переходов состояния |
| Бронирование | двойное бронирование, неверная отмена, несогласованность сторон | E2E бронирования, гонки, отмены и восстановления |
| Зависимости | известная уязвимость или несогласованный lockfile | security workflow |
| Нефункциональное качество | WCAG, производительность, визуальные изменения | отдельные GitHub Actions workflows |

## Уровни проверок

### Unit

Проверяют чистую бизнес-логику без браузера и внешнего стенда. Это самый быстрый и детерминированный уровень.

### API

Проверяют локальные HTTP-контракты без зависимости от доступности PomidorQA.

### E2E

Используются только там, где важен реальный пользовательский путь: авторизация, профиль, каталог, слоты, бронирование, отмена и межпользовательское состояние.

E2E выполняются с `workers=1` и `retries=0`.

## Подготовка и очистка данных

Каждый сценарий использует уникальные данные.

Если регистрация через UI не является предметом проверки, аккаунт создаётся через тестовый API. Созданный аккаунт привязывается к конкретному `APIRequestContext`; teardown удаляет только отмеченные тестовые аккаунты и затем закрывает `BrowserContext`.

Многопользовательские сценарии используют независимые контексты. Проверки адресуются к конкретному пользователю, навыку, слоту или бронированию, а не к случайному первому элементу.

## Синхронизация

После действия, меняющего состояние, тест ждёт наблюдаемый причинный сигнал:

- конкретный HTTP-ответ;
- переход по URL;
- изменение состояния интерфейса;
- Playwright auto-waiting;
- ограниченный повторный опрос только при подтверждённой eventual consistency.

Не используются `waitForTimeout`, произвольные паузы, `force: true` и повторные попытки только ради зелёного результата.

## Браузерная стратегия

Один и тот же E2E-набор выполняется в Chromium, Firefox и WebKit. `fail-fast: false` позволяет получить результат всех движков даже при сбое одного из них.

Различие между одним браузером и всеми тремя помогает отделять браузерную несовместимость от общего сбоя продукта или теста.

## Нефункциональные сигналы

Функциональные E2E не смешиваются с другими классами качества:

- Accessibility Audit — axe-core / WCAG;
- Performance Smoke / Lighthouse — технические показатели публичных страниц;
- Visual Regression — сравнение внешнего вида;
- Security & Quality Gates — зависимости и статические проверки.

## Обязательные проверки перед слиянием

Точный список задаётся ruleset `Protect main` и приведён в `docs/quality-gates.md`. Он включает Quality, Unit, API, три браузерных E2E и три security checks.

Telegram не является источником истины: он только доставляет уже известный результат.

## Плановые и диагностические запуски

- Nightly ищет регрессии, возникшие после слияния или из-за внешнего стенда;
- Stability повторяет выбранный сценарий с `retries=0`;
- Registration Contract Smoke вручную проверяет сетевой контракт регистрации;
- Telegram Notification Test вручную проверяет интеграцию уведомлений.

## Разбор красной проверки

1. Сохранить исходный запуск и доступные artifacts.
2. Найти первую реально упавшую проверку, а не финальное уведомление.
3. Определить слой: код теста, продукт, браузер/runtime, внешний стенд, зависимость или CI.
4. Посмотреть отчёт, trace, screenshots/video и сетевые данные.
5. Сравнить браузеры и соседние проверки.
6. Повторный запуск делать только при конкретном основании считать сбой внешним и временным.
7. Исправлять причину, а не ослаблять ожидания.

## Критерии готовности

Перед слиянием должны быть понятны назначение изменения и затронутый риск, данные должны быть изолированы, временная диагностика удалена, а обязательные проверки — зелёными на актуальном `main`.

Главный принцип:

> Использовать минимально достаточный уровень тестирования и оставлять E2E только для тех рисков, которым действительно нужен интегрированный пользовательский сценарий.
