# Карта test suites

Этот документ связывает основные риски проекта с конкретными test suites. Он нужен для навигации по репозиторию, ревью изменений и объяснения архитектуры проверок.

**Requirement coverage считается отдельно** в [`coverage-matrix.md`](./coverage-matrix.md) относительно 50 требований из [`requirements.md`](../requirements.md). Количество spec-файлов или тестов не подменяет процент покрытия требований.

Матрица ведёт traceability до конкретного case: для каждого проверяемого требования указана пара `test-файл → точное название test(...)`. `npm run coverage:check` валидирует не только наличие файла, но и существование указанного test case в его исходнике.

Источник истины — код в `main`. Текущий инвентарь: **10 Unit + 11 API + 100 E2E = 121 автоматизированная проверка**. Если меняется структура тестов, число проверок или зона ответственности spec-файла, эта карта и связанные метрики обновляются в том же Pull Request.

## Принципы покрытия

- Unit проверяет детерминированную логику без браузера и live-стенда.
- API включает локальные HTTP-контракты и отдельный live-контракт тестового API регистрации PomidorQA. API-контракты бронирования учитываются как автоматизированное покрытие соответствующих бизнес-правил; при этом документация явно отличает mock API от live-проверок.
- E2E используется для интегрированных пользовательских сценариев PomidorQA.
- Live E2E выполняется в Chromium, Firefox и WebKit с `workers=4` на браузер и `retries=0`; matrix ограничена `max-parallel: 2`, поэтому одновременно выполняются максимум две browser jobs, тестовые данные уникальны, а пользовательские сессии изолированы по `BrowserContext`.
- Тестовые данные уникальны; для setup предпочтителен API, если UI-регистрация не является предметом проверки.
- Созданные тестовые аккаунты удаляются централизованным teardown.

## Нефункциональные проверки вне spec-файлов

Отдельные GitHub Actions workflows покрывают другие классы риска:

- Accessibility Audit — axe-core / WCAG;
- Performance Smoke / Lighthouse — производительность публичных страниц;
- Security & Quality Gates — зависимости, SBOM и статические проверки;
- Nightly E2E Regression — плановая проверка внешнего стенда;
- Stability Check — повторные прогоны без retries;
- Registration Contract Smoke — ручная проверка точного HTTP-контракта регистрации;
- AI Review — проверка PR diff по `CODEX.md`/`REVIEW.md` после зелёного CI, с отдельной Summary и Telegram job;
- Telegram Notification Test — диагностика канала уведомлений.

## Как использовать карту

При добавлении нового теста сначала определить риск и минимально достаточный уровень. Новый E2E нужен только тогда, когда риск нельзя надёжно закрыть Unit/API-проверкой или уже существующим пользовательским сценарием.

При ревью важно проверять не количество новых тестов, а отсутствие дублирования, изоляцию данных, корректный cleanup и понятную связь сценария с риском.
