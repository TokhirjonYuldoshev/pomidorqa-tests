# AI Review

AI Review — дополнительный контроль Pull Request после успешного функционального CI. Он проверяет изменения по правилам `CODEX.md` и `REVIEW.md`, публикует подтверждённые замечания в PR и формирует отдельную Actions Summary.

## Когда запускается

Workflow `.github/workflows/ai-review.yml` работает в двух режимах:

- автоматически после успешного `Playwright QA Automation CI` для Pull Request;
- вручную через `workflow_dispatch` по номеру PR.

Push в `main` не используется как цель AI Review: проверяется именно Pull Request diff.

## Модель безопасности

Workflow имеет доступ к секрету Gemini и праву публикации review, поэтому код PR считается недоверенным.

Контроли:

- checkout выполняется только из доверенной ветки `main`;
- PR head не checkout-ится;
- зависимости из PR не устанавливаются;
- код PR не исполняется;
- artifacts из PR CI не скачиваются;
- PR и head SHA разрешаются через GitHub API;
- diff читается через GitHub API;
- inline-комментарии разрешены только на реально добавленных строках;
- перед публикацией повторно проверяется, что head SHA не изменился.

Telegram job не имеет права записи в Pull Request.

## Scope

Проверяются изменения в:

- `tests/`;
- `src/`;
- `scripts/`;
- `.github/workflows/`;
- `docs/`;
- `README.md`;
- `requirements.md`;
- `CODEX.md`;
- `REVIEW.md`;
- ключевых конфигурационных файлах.

Удалённые файлы и файлы без доступного patch не используются как основание для inline-комментария.

## Как формируется замечание

Первый проход модели получает:

1. метаданные PR как недоверенные данные;
2. `CODEX.md`;
3. `REVIEW.md`;
4. diff с номерами добавленных строк.

Комментарий допустим только при выполнении всех условий:

- путь входит в scope;
- строка действительно добавлена в PR;
- приоритет только `P1`, `P2` или `P3`;
- номер правила существует в `CODEX.md`;
- нарушение доказано diff;
- комментарий не является вкусовым предпочтением или предложением «на будущее».

Максимум публикуется пять inline-комментариев за один review.

## Второй проход

Кандидаты первого прохода проверяются повторно отдельным запросом модели. Второй проход не ищет новые проблемы — он только решает, доказан ли каждый уже найденный кандидат.

Если есть сомнение, замечание отклоняется. Это снижает риск ложных комментариев из-за:

- невидимого контекста;
- неверной строки;
- неверного файла;
- требования, которого нет в `CODEX.md`;
- игнорирования `finally` или гарантированного `afterEach`;
- стилевого предпочтения, выданного за дефект.

После второго прохода локальная валидация ещё раз проверяет координаты и номера правил перед отправкой в GitHub.

## Приоритеты

| Приоритет | Смысл |
| --- | --- |
| `P1` | критический дефект, потеря/утечка данных или разрушение ключевого сценария |
| `P2` | доказанное нарушение `CODEX.md`, которое требует исправления до merge |
| `P3` | реальное, но неблокирующее нарушение `CODEX.md` |

P1/P2/P3 не являются оценкой автора PR. Это классификация конкретного подтверждённого finding.

## Дедупликация и защита от устаревшего результата

В опубликованный review добавляется скрытый marker с head SHA.

Если тот же commit уже проверен, повторный вызов Gemini не выполняется. Если head PR изменился до или во время анализа, результат не публикуется.

## Actions Summary

Сводка показывает:

- PR и commit;
- состояние review;
- число подтверждённых замечаний;
- распределение P1/P2/P3;
- модель;
- размер diff;
- число файлов в scope;
- token usage;
- факт второго прохода;
- security controls;
- ссылку на опубликованный review.

## Telegram

Telegram вынесен в отдельную job `Telegram Notification`, которая зависит от job review через `needs`.

Сообщение содержит:

- итог выполнения workflow;
- номер PR и commit;
- состояние review;
- общее число findings;
- P1/P2/P3;
- число файлов и размер diff;
- модель и token usage;
- ссылку на опубликованный review, если она есть;
- ссылку на GitHub Actions run.

Ошибка Telegram не меняет результат AI Review.

## Ограничения

AI Review не заменяет CI, ручное чтение сложных изменений или требования продукта. Он работает только в пределах переданных правил и diff.

Если GitHub не возвращает patch, diff превышает установленный лимит или модель/API недоступны после ограниченного числа повторных запросов, workflow завершается с явной ошибкой вместо публикации неподтверждённого результата.
