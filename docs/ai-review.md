# AI Review

AI Review — дополнительный контроль Pull Request после успешного функционального CI. Он проверяет добавленные строки по `CODEX.md` и `REVIEW.md`, использует спецификацию продукта и coverage matrix как контекст, публикует подтверждённые замечания в PR и формирует отдельную Actions Summary.

## Когда запускается

Workflow `.github/workflows/ai-review.yml` работает в двух режимах:

- автоматически после успешного `Playwright QA Automation CI` для Pull Request;
- вручную через `workflow_dispatch` по номеру PR.

Для автоматического запуска сохраняется ID upstream CI. Это позволяет связать review с конкретным зелёным прогоном, после которого оно было создано.

Push в `main` не является целью AI Review: проверяется именно Pull Request diff.

## Модель безопасности

Workflow имеет доступ к секрету Gemini и праву публикации review, поэтому PR рассматривается как недоверенный ввод.

Контроли:

- checkout выполняется только из доверенной ветки `main`;
- PR head не checkout-ится;
- зависимости из PR не устанавливаются;
- код PR не исполняется;
- artifacts из PR CI не скачиваются;
- PR и head SHA разрешаются через GitHub API;
- diff читается через GitHub API;
- inline-комментарии разрешены только на реально добавленных строках;
- перед публикацией повторно проверяется, что head SHA не изменился;
- Telegram job имеет только `contents: read` и не может публиковать review.

## Scope

Проверяются изменения в:

- `tests/`;
- `src/`;
- `scripts/`;
- `.github/workflows/`;
- `docs/`;
- `README.md`;
- `requirements.md`;
- `CODEX.md`;
- `REVIEW.md`;
- ключевых конфигурационных файлах.

Summary отдельно показывает:

- сколько файлов изменено в PR;
- сколько вошло в review scope;
- сколько осталось вне scope;
- размер анализируемого diff.

Удалённые файлы и файлы без доступного patch не используются как основание для inline-комментария.

## Три уровня проверки

### 1. Детерминированный preflight

До обращения к модели добавленные строки проверяются на однозначные запреты из `CODEX.md`:

- `waitForTimeout(...)`;
- `force: true`;
- `test.only(...)` / `describe.only(...)`;
- `page.pause(...)`.

Эти нарушения не требуют вероятностной интерпретации. Finding привязывается к точному файлу, добавленной строке и правилу Кодекса.

Детерминированные findings имеют приоритет при формировании итоговых максимум пяти inline-комментариев. Этот preflight применяется только к Playwright-коду в `tests/**/*.ts`, чтобы строки из документации вроде `waitForTimeout` или `force: true` не создавали ложные findings. Поведение слоя проверяется отдельным `scripts/ai-review-self-check.mjs`, который запускается в Quality job до browser E2E и не входит в счётчик Playwright-проверок.

### 2. Основной проход модели

Модель получает:

1. метаданные PR как недоверенные данные;
2. `CODEX.md`;
3. `REVIEW.md`;
4. `requirements.md`;
5. `docs/coverage-matrix.md`;
6. diff с номерами добавленных строк.

`requirements.md` и coverage matrix используются как контекст ожидаемого поведения и traceability. Они не расширяют закрытый список правил для inline-комментариев: каждый комментарий по-прежнему обязан ссылаться на существующий номер `CODEX.md`.

Статусы `known defect`, `partial` и `out of scope` в матрице не трактуются как дефект текущего PR сами по себе.

### 3. Второй проход модели

Кандидаты основного прохода проверяются повторно отдельным запросом. Второй проход не ищет новые проблемы — он проверяет доказанность уже найденных кандидатов.

Finding сохраняется только если нарушение:

- прямо следует из `CODEX.md`;
- доказано показанным diff;
- относится к реально добавленной строке;
- не является стилевым предпочтением;
- не требует контекста, которого нет в данных review.

После этого локальная валидация ещё раз проверяет путь, номер строки, приоритет и номер правила.

## Traceability требований

AI Review строит дополнительный детерминированный сигнал по `docs/coverage-matrix.md`.

Если PR меняет test-файл, который указан как доказательство для requirement ID, Summary и Telegram показывают соответствующие ID. Например, изменение сценария бронирования может автоматически связаться с требованиями, для которых этот spec указан в колонке доказательств.

Это не меняет статус требования и не пересчитывает coverage. Источником статусов остаётся `docs/coverage-matrix.md`, а их согласованность отдельно проверяет `npm run coverage:check`.

## Правила публикации комментария

Комментарий допустим только при выполнении всех условий:

- путь входит в review scope;
- строка действительно добавлена в PR;
- приоритет только `P1`, `P2` или `P3`;
- номер правила существует в `CODEX.md`;
- нарушение доказано;
- комментарий не отрицает сам себя.

Максимум публикуется пять inline-комментариев. Совпадающие findings по одной координате и одному правилу дедуплицируются.

## Приоритеты

| Приоритет | Смысл |
| --- | --- |
| `P1` | критический дефект, потеря/утечка данных или разрушение ключевого сценария |
| `P2` | доказанное нарушение `CODEX.md`, которое требует исправления до merge |
| `P3` | реальное, но неблокирующее нарушение `CODEX.md` |

P1/P2/P3 относятся к конкретному finding, а не к автору PR.

## Дедупликация и защита от устаревшего результата

В опубликованный review добавляется скрытый marker с head SHA.

Если тот же commit уже проверен, повторный вызов Gemini не выполняется. Если head PR изменился до или во время анализа, устаревший результат не публикуется.

Каждый опубликованный review дополнительно фиксирует revision доверенного reviewer-кода из `main` и короткий SHA-256 fingerprint набора правил/контекста (`CODEX.md`, `REVIEW.md`, `requirements.md`, coverage matrix). Это позволяет понять не только какой PR commit проверен, но и какой именно набор reviewer-правил дал результат.

## Actions Summary

Сводка показывает:

- PR и commit;
- состояние review;
- число подтверждённых findings;
- распределение P1/P2/P3;
- число детерминированных findings;
- модель;
- размер diff;
- изменённые / проверенные / проигнорированные файлы;
- связанные requirement ID;
- upstream CI run;
- trusted reviewer revision;
- policy fingerprint по `CODEX.md` + `REVIEW.md` + `requirements.md` + coverage matrix;
- token usage;
- факт второго прохода;
- security controls;
- ссылку на опубликованный review.

## Telegram

Telegram вынесен в отдельную job `Telegram Notification`, которая зависит от job review через `needs`.

Сообщение содержит:

- итог выполнения workflow;
- номер PR и commit;
- состояние review;
- общее число findings;
- P1/P2/P3;
- число детерминированных findings;
- изменённые / проверенные / проигнорированные файлы;
- связанные requirement ID;
- размер diff;
- модель и token usage;
- ссылку на upstream CI;
- trusted reviewer revision;
- policy fingerprint;
- ссылку на опубликованный review, если она есть;
- ссылку на текущий GitHub Actions run.

Ошибка Telegram не меняет результат AI Review.

## Degraded mode

Gemini API является внешней зависимостью. После ограниченного числа retry на 408/429/5xx или network error workflow не выдаёт ложный полный вердикт и не публикует непроверенные модельные кандидаты. Вместо этого review переходит в состояние `degraded`: публикуются только детерминированные findings, Summary и Telegram явно отмечают, что полный модельный проход не выполнен. Если детерминированных findings нет, результат формулируется как «preflight нарушений не нашёл», а не как «нарушений вообще нет».

Ошибки схемы, локальной валидации, GitHub API или другие нетранзиентные ошибки по-прежнему завершают review job с ошибкой.

## Контрольный контракт end-to-end

После изменений reviewer-кода полезно подтверждать не только зелёный workflow, но и семантику результата. Контрольный Pull Request считается валидным, если одновременно выполняются условия:

- PR CI полностью зелёный;
- AI Review запущен именно после успешного upstream CI;
- в review body присутствуют commit PR, upstream CI, trusted reviewer revision и policy fingerprint;
- документационные упоминания `waitForTimeout` и `force: true` не создают deterministic findings, потому что preflight ограничен `tests/**/*.ts`;
- при отсутствии доказуемого нарушения CODEX итог содержит 0 findings;
- отдельная job `Telegram Notification` завершается независимо от review job;
- повторный запуск для того же head SHA не публикует второй review.

Такой контроль проверяет одновременно безопасность trusted-main схемы, отсутствие ложных deterministic findings, provenance результата, дедупликацию и транспорт уведомления.

## Ограничения

AI Review не заменяет CI, спецификацию продукта или ручное чтение сложного изменения. Он не должен придумывать требования и не меняет статусы coverage matrix.

Если GitHub не возвращает patch, diff превышает установленный лимит, нарушена схема данных или GitHub API возвращает нетранзиентную ошибку, workflow завершается с явной ошибкой. Временная недоступность Gemini обрабатывается через `degraded` mode без публикации неподтверждённых модельных замечаний.
