# Карта документации PomidorQA QA

Этот каталог организует портфельную документацию по инженерным решениям и эксплуатационным вопросам, не дублируя корневой `README.md`.

| Документ | Назначение | Когда использовать |
| --- | --- | --- |
| [Risk-Based Test Strategy](./test-strategy.md) | Определяет цели качества, модель рисков, границы ответственности, уровни тестирования, entry/exit criteria, triage ошибок и полезные метрики | когда нужно решить, что тестировать, на каком уровне, насколько глубоко и каких доказательств достаточно |
| [Quality Gates](./quality-gates.md) | Определяет обязательные merge-сигналы, неблокирующую диагностику и требования к evidence | при ревью PR, разборе CI или принятии решения о готовности к merge |
| [Architecture](./architecture.md) | Объясняет POM, fixtures, helpers, управление тестовыми данными, отчёты и архитектуру workflows | при изменении структуры фреймворка или разборе ownership ошибки |
| [CI Incident Runbook](./ci-incident-runbook.md) | Фиксирует ownership сигналов, severity, triage discipline и порядок разбора CI/regression incidents с сохранением evidence | при диагностике упавшего gate, live-регрессии, platform issue или observability failure |
| [Registration Contract Smoke](./registration-contract-smoke.md) | Описывает ручную проверку live HTTP-контракта регистрации | при диагностике точной цепочки `POST → 303 → /pomidorqa` |
| [Interview Guide](./interview-guide.md) | Превращает реализованные инженерные решения в короткие технические объяснения | при подготовке к собеседованию или техническому обзору проекта |

## Рекомендуемый порядок чтения

Для технического обзора репозитория:

1. начните с **Risk-Based Test Strategy**, чтобы понять, зачем существует набор тестов и какие риски он контролирует;
2. затем прочитайте **Quality Gates**, чтобы понять, какие сигналы блокируют merge, а какие являются диагностическими;
3. используйте **Architecture** для понимания структуры реализации и ownership компонентов;
4. обращайтесь к **CI Incident Runbook**, когда сигнал красный и важно определить владельца проблемы;
5. используйте **Registration Contract Smoke** для узкой диагностики live-контракта регистрации;
6. **Interview Guide** используйте как материал для объяснения уже реализованных решений, а не как источник требований.

## Принципы документации

- Зелёный pipeline — это evidence, а не доказательство отсутствия дефектов.
- Поведение продукта, состояние внешнего окружения и здоровье тестовой инфраструктуры рассматриваются как разные сигналы.
- Критичные live-сценарии синхронизируются по наблюдаемым причинным сигналам, а не по произвольным sleeps или blind retries.
- Документация описывает реализацию, которая реально находится в `main`; нереализованные возможности не выдаются за готовые.
- Изменения runtime contracts, quality gates, incident ownership или test ownership должны обновлять соответствующий документ в том же Pull Request.
