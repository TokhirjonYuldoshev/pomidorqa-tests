# QA Automation Interview Guide

Этот документ связывает архитектурные решения проекта с вопросами, которые могут возникнуть на техническом собеседовании. Ответы ниже описывают не абстрактный «идеальный проект», а решения, которые действительно используются в этом репозитории.

Главное правило на собеседовании: сначала дать короткий ответ, затем раскрывать детали только если интервьюер спрашивает глубже.

## Почему Playwright?

### Короткий ответ

Я выбрал Playwright, потому что он хорошо подходит для современного E2E-тестирования: поддерживает Chromium, Firefox и WebKit, имеет встроенные auto-waiting, browser contexts, trace/screenshot/video diagnostics и удобную интеграцию с TypeScript и CI.

В этом проекте один E2E-suite запускается на трёх браузерных движках, а browser context используется для изоляции пользователей внутри одного сценария.

### Если попросят подробнее

Для меня важны несколько возможностей Playwright:

- встроенное ожидание actionable-состояния элемента вместо ручных sleep;
- изолированные browser contexts без запуска отдельного браузера для каждого пользователя;
- удобная работа с network response и navigation signals;
- единый API для Chromium, Firefox и WebKit;
- trace, screenshot и video для диагностики CI failures;
- fixtures и projects в самом test runner;
- хорошая TypeScript-поддержка.

Playwright выбран не потому, что «он новее Selenium», а потому что его модель синхронизации и контекстов хорошо подходит под сценарии этого проекта.

## Почему Fixtures?

### Короткий ответ

Fixtures я использую для управления lifecycle тестового окружения. В проекте они централизованно создают и закрывают browser contexts, поэтому E2E-spec отвечает за бизнес-сценарий, а не за технический setup и teardown.

Для booking-сценариев есть role fixtures вроде `hostApp`, `guestApp`, `guest2App`, а `appFactory` позволяет создать произвольное количество изолированных пользователей.

### Если попросят подробнее

Главная задача fixtures здесь — ownership ресурсов.

Если каждый spec самостоятельно создаёт contexts и закрывает их в `finally`, логика lifecycle начинает дублироваться. Это повышает риск browser-context leaks и усложняет тесты.

Поэтому:

1. fixture создаёт или регистрирует `AppContext`;
2. spec получает готовый объект для сценария;
3. после теста fixture централизованно выполняет cleanup;
4. ошибка cleanup не скрывается обычным warning.

Если setup падает уже после создания context, helper закрывает созданный context до повторного выброса исходной ошибки.

## Почему retries отключены?

### Короткий ответ

В основном CI E2E запускаются с `retries=0`, потому что retry может скрыть нестабильность и превратить реальный первый failure в зелёный pipeline.

Мне важнее получить честный сигнал: если тест упал, причина должна быть исследована, а не автоматически замаскирована повторным запуском.

### Если попросят подробнее

Я не считаю retries «плохими всегда». Они могут быть допустимы в определённой инфраструктуре, но в этом portfolio-проекте я специально использую строгий gate.

Разделение такое:

- required CI: `retries=0` — максимально честный release signal;
- Stability workflow: многократные повторы через `repeat-each`, также с `retries=0`, чтобы именно измерять стабильность;
- Nightly regression: `retries=0`, чтобы ночной regression failure не исчезал после повторной попытки.

Если тест становится flaky, я сначала ищу источник нестабильности: locator, test data, synchronization, shared state или eventual consistency.

## Как боролись с flaky tests?

### Короткий ответ

Я не стабилизирую тесты через `waitForTimeout`, `force` или скрытые retries. Использую наблюдаемые сигналы приложения: HTTP response, URL transition, появление или исчезновение нужного UI-состояния и Playwright auto-waiting.

Также тесты получают уникальные данные и изолированные browser contexts. Для проверки стабильности есть отдельный stress workflow с `repeat-each` и разным количеством workers.

### Если попросят подробнее

В проекте применены несколько уровней защиты от flaky-поведения:

- уникальный `runId` на сценарий;
- точные locators вместо выбора «первого подходящего» элемента;
- browser-context isolation;
- ожидание конкретного mutation response для state-changing действий;
- polling/reload только там, где подтверждена реальная eventual consistency;
- централизованный teardown;
- `retries=0`;
- отдельные stability runs: repeat 5/10, workers 1/2.

Перед включением strict CI gate booking-flow и весь E2E-suite отдельно прогонялись многократно без retries.

## Как устроен CI?

### Короткий ответ

Основной CI разделён по слоям. Сначала независимо проходят Quality, Unit и API. После них запускается E2E browser matrix в Chromium, Firefox и WebKit. Каждый browser job работает с одним worker и без retries.

После E2E сохраняются Playwright HTML и Allure reports. Отдельно публикуется CI Summary и отправляется итоговое Telegram-уведомление.

### Если попросят подробнее

Упрощённая схема:

```text
Pull Request / push main
        |
        +--> Quality: ESLint + TypeScript
        +--> Unit tests
        +--> API tests
                 |
                 v
             E2E Matrix
        +--------+--------+
        |        |        |
    Chromium  Firefox   WebKit
        |        |        |
        +---- Reports ----+
                 |
        Summary + Telegram
```

`fail-fast: false` у browser matrix позволяет получить результат всех трёх движков, даже если один из них упал.

Основной CI дополняют два независимых pipeline:

- Nightly regression — полный E2E-suite по расписанию;
- Security & Quality Gates — dependency/security и code-quality проверки.

## Почему POM?

### Короткий ответ

Page Object Model использую для отделения UI-деталей от бизнес-сценария. Locators и действия экрана находятся в Page Objects, а assertions бизнес-результата остаются в spec.

Так тест читается как сценарий, а изменение локатора обычно требует правки в одном месте.

### Если попросят подробнее

Я стараюсь не превращать Page Object в «второй тестовый фреймворк».

Разделение ответственности такое:

- spec — бизнес-шаги и assertions;
- Page Object — locators, UI actions и техническая синхронизация;
- helper — повторяемая domain preparation;
- fixture — lifecycle;
- test-data factory — уникальные данные.

Page Object может проверить технический precondition действия. Например, если booking-сценарий сам создаёт ровно один слот, `pickOnlyAvailableSlot()` проверяет, что доступен действительно один день и один слот, вместо молчаливого выбора `.first()`.

## Как генерируются тестовые данные?

### Короткий ответ

Каждый сценарий получает уникальный `runId`. Связанные сущности используют один run id, но разные роли — например host, guest и guest2.

Это предотвращает конфликты между запусками и одновременно позволяет быстро понять по логам, какие данные относятся к одному сценарию.

### Если попросят подробнее

Принцип примерно такой:

```text
runId = booking-flow-<unique>

host  + runId
guest + runId
guest2 + runId
skill + runId
```

Это важно для live-стенда, где данные разных CI-runs могут существовать одновременно.

Я не ищу случайную существующую карточку или слот. Сценарий создаёт необходимые preconditions сам и затем идентифицирует сущность по уникальным данным.

Это также помогает сохранить независимость тестов: один тест не должен рассчитывать на данные, созданные другим тестом.

## Для чего используется Allure?

### Короткий ответ

Для анализа результатов использую Allure Report. Он генерируется после E2E-run и сохраняется как GitHub Actions artifact отдельно для каждого браузера. Параллельно оставлен встроенный Playwright HTML report.

### Если попросят подробнее

Playwright HTML удобен как быстрый нативный отчёт, а Allure добавляет отдельный reporting layer.

Pipeline выглядит так:

```text
Test Execution
      |
      v
Allure Results
      |
      v
Allure Report
      |
      v
GitHub Actions Artifact
```

Allure report генерируется и после failed E2E-run, если workflow не был отменён. Поэтому его можно использовать именно для failure analysis.

## Зачем Browser Matrix?

### Короткий ответ

Один и тот же E2E-suite запускается в Chromium, Firefox и WebKit, чтобы проверять не только бизнес-логику, но и browser-specific поведение.

Jobs независимы и используют `fail-fast: false`, поэтому падение одного браузера не лишает меня информации о двух остальных.

### Если попросят подробнее

Browser выбирается через `E2E_BROWSER`, а Playwright config подставляет соответствующее desktop device preset.

Для каждого движка CI сохраняет отдельные Allure и Playwright artifacts. Это позволяет быстро понять, является failure общим или специфичным для браузера.

## Зачем Nightly Regression, если есть CI на PR?

### Короткий ответ

PR CI отвечает на вопрос «безопасно ли сливать это изменение сейчас». Nightly regression отвечает на другой вопрос: «не сломалось ли что-то на live-стенде после merge или из-за внешних изменений».

Поэтому nightly вынесен в отдельный workflow и каждый день выполняет полный E2E-suite на трёх браузерах.

### Если попросят подробнее

Nightly запускается по cron `0 23 * * *`: GitHub Actions использует UTC, поэтому запуск в 23:00 UTC соответствует **02:00 локального времени UTC+3 следующего дня**. Также поддерживается ручной запуск.

Он использует:

- Chromium, Firefox, WebKit;
- 1 worker на браузер;
- `retries=0`;
- Allure и Playwright reports;
- failure diagnostics.

Nightly не заменяет required PR checks и не делает merge gate менее строгим.

## Какие Security & Quality Gates есть в проекте?

### Короткий ответ

Есть отдельный security workflow. Он выполняет `npm audit` с порогом high, проверяет изменения dependency manifests в pull request и отдельно запускает ESLint + TypeScript.

Security pipeline дополняет тестовый CI, а не заменяет его.

### Если попросят подробнее

На pull request dependency-change job сравнивает `package.json` и `package-lock.json` между base и head.

Если зависимости изменились:

1. выполняется `npm ci`, что одновременно проверяет согласованность lockfile;
2. выполняется `npm audit --audit-level=high`;
3. high/critical vulnerability делает gate красным.

Если manifests не менялись, job явно фиксирует это и завершается без лишней работы.

Решение не зависит от включённого GitHub Dependency Graph, поэтому workflow переносим между репозиториями.

## Почему один worker в E2E?

### Короткий ответ

E2E работают с общим live-стендом, поэтому я сознательно использую один worker на браузер в required CI. Это уменьшает инфраструктурный шум и делает failure signal более детерминированным.

При этом параллельное поведение отдельно исследовалось в Stability workflow с workers 1 и 2.

## Почему нельзя просто использовать `.first()`?

### Короткий ответ

`.first()` опасен, если тест должен найти конкретную бизнес-сущность. Он может выбрать не того пользователя, слот или карточку и дать ложный результат.

Поэтому я создаю уникальные данные и использую точную идентификацию. Если сценарий ожидает единственный слот, Page Object сначала проверяет precondition «слот действительно один».

## Unit, API и E2E — зачем все три уровня?

### Короткий ответ

Они дают разный тип сигнала. Unit быстро проверяют чистую логику, API проверяют HTTP-поведение без UI, а E2E подтверждают реальный пользовательский сценарий через live UI.

Я не пытаюсь проверять всё через браузер: это было бы медленнее и сложнее диагностировать.

## Как бы вы расследовали красный E2E в CI?

### Короткий ответ

Сначала определил бы масштаб: падает один браузер или все три. Затем посмотрел бы assertion/error, Allure или Playwright HTML report, trace, screenshot/video и сетевой сигнал вокруг места падения.

После этого проверил бы, относится ли проблема к продукту, тестовым данным, locator/synchronization или инфраструктуре. Retry не использовал бы как первое «исправление».

> Это standalone QA Automation-проект на Playwright и TypeScript. В нём есть Unit, API и E2E уровни, Page Objects, fixtures, helpers и генерация уникальных тестовых данных. Основной CI запускает quality checks, Unit/API, а затем E2E matrix в Chromium, Firefox и WebKit без retries. Для диагностики сохраняются Playwright и Allure reports. Отдельно есть nightly regression, stability workflow для исследования flaky-поведения и security gates для зависимостей и code quality. Основной акцент проекта — не количество тестов, а воспроизводимый и честный тестовый сигнал.

Не нужно заучивать формулировку дословно. Важно понимать, почему каждое решение находится в проекте и какую проблему оно решает.
