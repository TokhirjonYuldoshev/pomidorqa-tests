# Архитектура тестовой системы

Документ описывает текущее устройство проекта и границы ответственности его слоёв.

## Цели архитектуры

Система должна обеспечивать независимые сценарии, точную идентификацию данных, управляемый жизненный цикл браузерных контекстов, обязательную очистку тестовых аккаунтов и понятную диагностику сбоев без скрытых retries и пауз.

## Общая схема

```text
E2E spec
  |
  +--> fixtures --> AppContext --> Page Objects --> PomidorQA UI
  |
  +--> helpers --> подготовка данных / API
  |
  +--> expect --> бизнес-проверки

teardown
  |
  +--> удаление отмеченного тестового аккаунта
  +--> закрытие BrowserContext
```

## `tests/e2e`

Здесь остаются пользовательский сценарий, `test.step` и бизнес-проверки.

Сейчас E2E сгруппированы по областям: авторизация/сессия, профиль, свободные слоты, каталог/поиск, доступность после бронирования, основной путь бронирования и отмена.

Разделение файлов по рискам позволяет развивать покрытие без одного огромного spec-файла.

## `tests/pages`

Page Objects содержат локаторы и действия экрана. Бизнес-проверки остаются в spec.

Метод страницы описывает смысл действия: сохранить профиль, добавить навык, открыть каталог, выбрать конкретный слот, отменить встречу. Если действие требует технического условия, Page Object может проверить это условие и выдать диагностическую ошибку.

## `tests/helpers`

Основные обязанности:

- `routes.ts` — маршруты;
- `test-data.ts` — уникальные идентификаторы;
- `user.ts` — модель пользователя, UI/API-регистрация и удаление тестового аккаунта;
- `booking.ts` — `AppContext`, создание и полная очистка контекстов;
- `catalog.ts` — повторяемая подготовка участников каталога.

Helper не должен скрывать бизнес-проверку, которая должна быть видна в тестовом сценарии.

## `tests/fixtures`

`appFactory` создаёт произвольное число независимых `AppContext` и регистрирует их для teardown.

Именованные fixtures (`hostApp`, `guestApp`, `guest2App`) используются там, где это делает многопользовательский сценарий понятнее.

## `AppContext` и очистка

`AppContext` объединяет `BrowserContext`, `Page` и нужные Page Objects.

При создании аккаунта через API или UI соответствующий `APIRequestContext` помечается как владелец тестового аккаунта. При завершении теста:

1. выполняется `deleteCurrentTestUser` только для отмеченного контекста;
2. затем закрывается `BrowserContext`;
3. ошибки очистки не скрываются и агрегируются.

Если аккаунт не создавался, лишний DELETE не отправляется.

## Тестовые данные

Связанные сущности одного сценария используют общий `runId`, но разные роли:

```text
runId
├── host
├── guest
├── guest2
├── skill
└── slot
```

Это предотвращает коллизии и упрощает разбор логов.

## Подготовка через API

UI-регистрация используется, когда проверяется сама регистрация. Для остальных сценариев предпочтителен `registerUserViaApi`, после которого UI проверяет уже нужное бизнес-поведение.

Так уменьшается длительность теста и число лишних UI-зависимостей, но сам пользовательский путь не подменяется API там, где UI и есть предмет проверки.

## Синхронизация

Основные допустимые сигналы:

- конкретный mutation response;
- URL transition;
- появление/исчезновение нужного элемента;
- Playwright auto-waiting;
- ограниченный polling/reload при подтверждённой eventual consistency.

Запрещено использовать `waitForTimeout`, `force: true`, `.only`, `skip` или CI retries как способ скрыть проблему.

## Каталог как отдельная область риска

Покрытие каталога разделено на несколько групп:

- базовый поиск и фильтрация;
- семантика строки поиска;
- граничные и специальные данные;
- изменения состояния профиля;
- правила доступности по слотам;
- каскадные изменения после бронирований и удаления аккаунтов.

Так проверяется не только «карточка нашлась», но и согласованность каталога с реальным состоянием пользователя.

## Бронирование

Основной сценарий проверяет гонку двух пользователей за один слот: первое подтверждение успешно, второе отклоняется.

Отдельные сценарии проверяют отмену, восстановление доступности, повторное бронирование освобождённого слота и каскадное удаление связанного состояния.

## Авторизация и сессия

Проверяется не только вход, но и границы доступа: защищённые страницы для анонимного пользователя, сохранение сессии, logout, независимость отдельных браузерных контекстов и отсутствие влияния одной сессии на другую.

## CI

Основной поток:

```text
Quality + Unit + API
          |
          v
E2E Chromium / Firefox / WebKit
          |
          v
Playwright HTML + Allure + диагностика
```

Для E2E: `workers=1`, `retries=0`, `fail-fast: false`.

Отдельный workflow безопасности даёт независимый сигнал по зависимостям и статическим проверкам.

## Нефункциональные проверки

Accessibility, Lighthouse и Visual Regression находятся в отдельных workflows и не смешиваются с функциональными E2E.

Nightly проверяет внешний стенд по расписанию. Stability повторяет выбранные сценарии без retries. Registration Contract Smoke и Telegram Notification Test запускаются вручную для узкой диагностики.

## Отчёты

Allure и Playwright HTML используются вместе. При падении E2E дополнительно сохраняются trace, screenshots, video и `test-results`.

Отчёт помогает понять причину, но не меняет результат проверки.
