# Правила внесения изменений

Репозиторий развивается как самостоятельный портфельный проект по автоматизации тестирования PomidorQA.

## Основной процесс

Изменения в `main` проходят через отдельную ветку и Pull Request. Для истории используется squash merge.

Рекомендуемые префиксы веток:

- `test/` — новые или переработанные тесты;
- `fix/` — исправление дефекта;
- `refactor/` — изменение структуры без смены поведения;
- `docs/` — документация;
- `chore/` — служебные изменения;
- `feature/` — новая функциональность тестовой инфраструктуры.

## Подготовка окружения

Проект использует Node.js 24.

```bash
git checkout main
git pull --ff-only origin main
nvm use 24
npm ci
```

Для E2E по умолчанию нужен Chromium:

```bash
npx playwright install chromium
```

Для проверки во всех браузерах:

```bash
npx playwright install chromium firefox webkit
```

## Проверки перед Pull Request

Быстрая локальная проверка без внешнего стенда:

```bash
npm run verify:local
```

Она включает проверку Node.js 24, ESLint, TypeScript, Unit и API.

E2E запускается отдельно:

```bash
npm run test:e2e
```

Не нужно многократно перезапускать упавший E2E до случайного зелёного результата. Сначала сохраняется исходный сбой и определяется его причина.

## Правила E2E

- сценарий и бизнес-проверки находятся в `tests/e2e`;
- локаторы и действия экранов — в `tests/pages`;
- повторяемая подготовка и данные — в `tests/helpers`;
- `tests/fixtures` владеет созданием и очисткой браузерных контекстов;
- регистрация через UI используется только когда сама регистрация является предметом проверки;
- для остальных сценариев предпочтительна подготовка аккаунта через тестовый API;
- каждый созданный тестовый аккаунт должен быть удалён даже при падении проверки;
- данные должны быть уникальными;
- многопользовательские сценарии используют отдельные `BrowserContext`;
- конкретная бизнес-сущность выбирается точным локатором, а не случайным `.first()`;
- `waitForTimeout`, `force: true`, `.only`, `skip` и `page.pause()` не используются для маскировки проблем;
- `retries=0` не ослабляется без документированной причины.

Подробные правила курса находятся в [CODEX.md](CODEX.md), а чек-лист ревью — в [REVIEW.md](REVIEW.md).

## Что должно быть в Pull Request

Описание отвечает минимум на три вопроса:

1. Что изменено?
2. Какой риск или задача этим закрывается?
3. Какими проверками подтверждён результат?

Не смешивайте в одном PR несвязанные изменения. При известном ограничении укажите его прямо, не скрывая повторными попытками или увеличением таймаута.

## Обязательные проверки

До слияния должны быть зелёными проверки, заданные ruleset `Protect main`. Их точный список приведён в [docs/quality-gates.md](docs/quality-gates.md).

## Отчёты

Playwright HTML и Allure формируются штатно. При ошибке сначала изучаются отчёты, trace, screenshots/video и сетевые сигналы, затем исправляется причина.

## Документация

Если изменение меняет архитектуру, правила подготовки данных, обязательные проверки, диагностические процессы или пользовательское покрытие, соответствующая документация обновляется в том же PR.
